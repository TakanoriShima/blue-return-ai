# blue-return-ai

個人事業主の青色申告に必要な経理作業を、Python と生成 AI で支援するプロジェクトです。

形式の異なる売上関連資料を共通の売上データ形式へ整理し、銀行入金との照合や青色申告用の経理を支援することを目指しています。

> **Status: 開発中（2026 年分の実データ処理を優先）**
> 請求書 Excel・銀行 CSV・クレジットカード CSV を年間一括で取り込み、共通形式の CSV と要確認一覧を出力するところまで実装済みです（「[現在できること](#現在できること)」を参照）。
> 売上と入金の照合、仕訳、帳簿、青色申告決算書向けの集計、PDF・LMS の自動取込、家事按分、生成 AI による処理は **まだ実装していない今後の計画** です。

## 目的

- **第一の目的**：2026 年分の実際の青色申告に使用できる会計データを完成させる。
- **第二の目的**：その過程で作った仕組みを匿名化・一般化し、公開可能なポートフォリオにする。

個人事業主の日々の経理作業（売上管理・入金確認・経費整理・仕訳作成）を、Python で効率化することを目指します。生成 AI は、必要性が確認できた部分にだけ導入する方針です。

申告そのものを AI に任せることは目的としていません。国税庁の確定申告書等作成コーナー・e-Tax 等につなげるための **経理支援ツール** を目指します（詳しくは「[最終的な出口：確定申告へのつなぎ方](#最終的な出口確定申告へのつなぎ方)」を参照）。

## 背景：売上関連資料は形式がそろっていない

個人事業主の売上は、案件によって手元に残る資料の形式が異なります。本プロジェクトでは、少なくとも以下の 3 パターンを想定しています。

| パターン | 資料 | 取得元 | 想定する読み取り方法 |
| --- | --- | --- | --- |
| A. 自分で請求書を作成する | 請求書 | Excel（取引先ごとに書式が異なる） | 元の Excel から読み取る（PDF は使わない） |
| B. 取引先が支払明細を発行する | 支払明細 | PDF | ローカルでのテキスト抽出 |
| C. LMS 上で実績を確認・承認する | 実績・報酬の明細 | LMS 画面からコピーしたテキスト | テキストを解析 |

これらを **共通の売上データ形式** に変換し、その後の検証・入金照合・帳簿作成を同じ仕組みで扱えるようにします。

## 想定する処理フロー

### 売上

```
Excel 請求書 / PDF 支払明細 / LMS 実績テキスト
  ↓
共通の売上データ形式へ変換
  ↓
検証（金額の整合性・日付の妥当性・欠落項目）
  ↓
人間による確認
  ↓
銀行明細の入金との照合候補
  ↓
人間による確認
  ↓
入金確定
```

源泉徴収や振込手数料の差し引きにより、請求額と実際の入金額は一致しないことがあります。そのため、「源泉徴収等を差し引く前の総額」と「振り込まれると期待される金額」を区別して扱います。

### 経費

```
銀行明細 / クレジットカード明細 / 家事関連費
  ↓
取引抽出
  ↓
勘定科目・仕訳候補
  ↓
人間による確認
  ↓
帳簿・決算用データ
```

## 最終的な出口：確定申告へのつなぎ方

本プロジェクトの当面の最終目標は、**国税庁の「確定申告書等作成コーナー」へ正確に入力できる状態まで、経理データを整理・集計すること** です。

### 全体の流れ

```
請求書・支払明細・LMS 実績
  ↓
共通売上データ
  ↓
銀行明細との入金照合
  ↓
経費データ
  ↓
仕訳
  ↓
帳簿
  ↓
決算集計
  ↓
青色申告決算書の作成に必要な入力情報        ← blue-return-ai が目指す範囲はここまで
  ↓
国税庁「確定申告書等作成コーナー」          ← ここから先は人間が行う
  ↓
青色申告決算書・所得税確定申告書
  ↓
e-Tax
```

blue-return-ai が担当するのは「経理資料の整理 → 検証 → 集計 → 申告書作成の支援」までです。確定申告書等作成コーナーへの入力、申告内容の最終確認・判断、e-Tax による送信は、人間が行います。

### 想定する出力（将来）

将来的には、確定申告書等作成コーナーへの入力に使う「確定申告入力用の集計データ」を出力できる構造を想定しています。例えば次のような情報です。

- 年間売上
- 必要経費の科目別集計
- 売掛金等の期末残高
- 事業用資産・負債等の残高
- 青色申告決算書の作成時に必要となるその他の集計情報

これらの具体的な項目・計算方法は、今後、国税庁の公式資料を確認しながら設計します。現時点では決まっていません。

### e-Tax との関係

- blue-return-ai は、e-Tax へ直接申告すること、および独自に e-Tax 用ファイルを生成して自動送信することを目的としていません。
- blue-return-ai が出力するデータは、e-Tax や確定申告書等作成コーナーへ直接取り込める形式ではありません。
- 国税庁が提供する公式なデータ形式・連携仕様を利用したデータ連携の可能性については、将来の調査対象とします。現時点で実装の予定はありません。

## 現在できること

### 年間一括処理（主な使い方）

`python -m blue_return_ai.annual --year 2026` で、`data/` 配下の資料から年間データを **毎回全件作り直します**。

```
data/invoices/     Excel 請求書（.xlsx）  ── テンプレートで読み取り ─┐
data/credit-card/  カード利用明細 CSV      ── 書式定義で読み取り ───┼─→ 共通形式の CSV ＋ 要確認一覧
data/bank/         銀行入出金明細 CSV      ── 書式定義で読み取り ───┘
```

- 取込方法は設定ファイル（`data/config/annual.json`）で、汎用の識別子で指定します（記入例：`sample_data/config/annual.example.json`）。
  - Excel 請求書：`template_a` / `template_b` / `template_c` / `template_instructor`。複数指定した場合は、ブックの **シート名** で振り分けます（ファイル名・取引先名・金額では判定しません）。
  - カード CSV：`card_csv_a`、銀行 CSV：`bank_csv_a`（文字コード・ヘッダー行・列名は設定で上書き可能）。
- Excel 請求書の各テンプレートは、ラベルの構成で書式を確認し、合わない場合は推測せず要確認（`TEMPLATE_LABEL_MISMATCH`）にします。
  - `template_c` は、同じシート名で集計欄の構成が異なる 5 つのパターン（A〜E）を、ラベルの集合で判定します。
  - Excel の日付シリアル値は、openpyxl の変換機能で日付にします。
- PDF からは売上を作りません（Excel との二重計上を防ぐため）。PDF は資料一覧で「要対応」として残ります。
- 取引の分類（事業・私用・カード引落等）は推測せず、すべて「未判断」として要確認一覧に出します。
- 売上計上日（`revenue_date`）は設定せず、「未確定」として要確認一覧に出します。

出力（`data/output/annual/<実行ID>/`。毎回新しいフォルダに作り、上書きしません）

| ファイル | 内容 |
| --- | --- |
| `sales.csv` / `sales_line_items.csv` | 共通形式の売上と明細（帳票パターン、意味を確定しない確認用の値を含む） |
| `card_transactions.csv` | カードの全取引（利用日・利用金額・今回の支払金額を区別） |
| `bank_transactions.csv` | 銀行の全取引（出金額と入金額を区別。空欄は null、0 は 0） |
| `unresolved_items.csv` | 全工程の要確認（警告コード・対象項目・判断を記入する列） |
| `documents_inventory.csv` | 全資料の一覧と取込状況（imported / manual / cross_check_only / unsupported / unresolved） |
| `manifest.json` | 件数・設定の SHA-256 など（ファイル名・値は含まない） |

- 取引は `source_key`（内容から作る安定キー）で識別し、期間の重なる CSV に同じ取引があっても二重登録しません。同じファイル内のまったく同じ取引は消さず、内容の近い取引は「重複候補」として要確認に出します。
- 資料単位の扱い（手入力で対応した・照合用のみ等）は、`data/decisions/documents.csv`（`sha256,status,note`）に人間が記入すると、次回の実行から反映されます。
- 画面には件数・警告コード別件数だけを表示します（取引先名・金額・ファイル名は表示しません）。

### 1 ファイルずつの確認（`blue_return_ai.cli`）

架空のサンプル請求書を 1 件ずつ共通売上データ（JSON と確認用 CSV）に変換する、初期段階から残している CLI です（`template_a` / `template_b` 用）。

### 構造確認ツール（`blue_return_ai.inspect_structure`）

実データの **値を表示せずに**、Excel / CSV の構造（セル番地・型・列数・文字コード等）だけを確認するツールです。本人がローカルで実行し、パーサーの実装に必要な情報を得るために使います（[docs/inspect_structure.md](docs/inspect_structure.md)）。

データ項目と検証ルールの詳細は [docs/data_model.md](docs/data_model.md) を参照してください。

## セットアップ

Python 3.12 以上が必要です。以下は Windows + Git Bash の例です。

```bash
git clone <このリポジトリの URL>
cd blue-return-ai

python -m venv .venv
source .venv/Scripts/activate   # macOS / Linux の場合: source .venv/bin/activate

pip install -e .                # blue_return_ai パッケージと依存（openpyxl）をインストール
pip install pytest              # テストを実行する場合
```

`pip install -e .` の後は、`PYTHONPATH` を指定せずに `python -m blue_return_ai.annual` などで実行できます。

## 使い方

### 年間一括処理（実データ。本人がローカルで実行）

```bash
mkdir -p data/config
cp sample_data/config/annual.example.json data/config/annual.json   # 初回のみ。必要に応じて編集
python -m blue_return_ai.annual --year 2026
```

- 実行のたびに `data/output/annual/<実行ID>/` に全件を作り直します。年末に資料を追加した場合も、同じコマンドを再実行します。
- 出力 CSV には実データが含まれます。外部（Claude Code 等の外部 AI を含む）に渡さないでください。

### サンプルデータでの実行例（1 ファイルずつ）

リポジトリには、架空の請求書 `sample_data/invoices/template_a_sample.xlsx` と `sample_data/invoices/template_b_sample.xlsx` が含まれています。

```bash
python -m blue_return_ai.cli sample_data/invoices/template_a_sample.xlsx --target-year 2026
python -m blue_return_ai.cli sample_data/invoices/template_b_sample.xlsx --template template_b --target-year 2026
```

画面には、件数・`record_id`・`review_status`・警告コードのみが表示されます（取引先名や金額は表示しません）。

#### 出力先

既定では `data/output/` 以下に出力します。

```
data/output/
├── records/<record_id>.json             # 1 請求書 = 1 ファイルの共通売上データ
└── review/<実行日時>_records.csv        # 人間確認用 CSV（1 行 = 1 請求書）
    review/<実行日時>_line_items.csv     # 人間確認用 CSV（1 行 = 1 明細）
```

- `data/output/` は実運用データを含み得るため、`data/` 全体と同様に **Git 管理対象外** です。
- 出力先は `--out-dir` で変更できますが、リポジトリ内では `data/` 配下以外への出力を拒否します（実データが Git 管理対象に紛れ込まないようにするため）。
- 確認用 CSV は Excel で開きやすい UTF-8（BOM 付き）です。`=` 等で始まる文字列は、Excel で数式として解釈されないようエスケープして出力します。
- 出力済みファイルは上書きしません。

#### 同じファイルを再度処理した場合（`cli` の場合）

`cli` は追記型で、元ファイルの内容から計算した `source_hash`（SHA-256）が、出力先の既存データと一致した場合は、**重複取込候補** として新しい売上データを作らずにスキップします。

- 売上データを識別する `record_id` は、`source_hash` とは独立した UUID です。
- サンプルデータの試行結果を実運用の出力と分けたい場合は、`--out-dir data/sample_output` のように別の出力先を指定してください。
- 年間一括処理（`annual`）は追記型ではなく、毎回全件を新しいフォルダに作り直します。

### review_status の意味（共通）

| 値 | 意味 |
| --- | --- |
| `unreviewed` | 機械的な検証では問題を検出していないが、人間はまだ確認していない |
| `needs_review` | 警告・エラー・重要な項目の欠落などがあり、人間による確認が必要 |
| `reviewed` | 人間が確認済み（**プログラムは設定しない**） |

`unreviewed` は「問題が無いと確定した」状態ではありません。どちらの場合も、人間が確認して初めて確定扱いになります。売上計上日（`revenue_date`）もプログラムは設定せず、人間が確定します。

## Human-in-the-loop の考え方

- プログラムや AI が出力する売上データ・勘定科目分類・仕訳・入金照合結果は、すべて **「候補」** として扱います。
- 重要な会計処理は、必ず人間が確認・承認してから確定します。
- 税務上の判断が必要な項目（例：売上計上日）は、プログラムが自動で決定せず、人間が確定します。
- 元資料から取得できない値は推測で埋めず、「不明」として人間の確認に回します（「無い（0）」と「不明（null）」を区別します）。
- 年間処理では、要確認の項目を `unresolved_items.csv` に集めます。人間の判断は出力とは別のファイル（`data/decisions/`）に保存し、再実行のたびに反映する設計です（現時点で反映されるのは資料単位の判断のみ）。
- 確定申告に関する最終確認・判断・送信は、人間が行います。blue-return-ai は、税務判断や申告そのものを自動化するシステムではありません。

## セキュリティ / プライバシー方針

- 実際の請求書・支払明細・銀行明細・クレジットカード明細などは `data/` に置き、Git 管理対象外とします。
- `.env`、API キー、認証情報はリポジトリに含めません。
- 公開用のデータは `sample_data/` に、実データのマスキングではなく **最初から架空の人物・企業・金額** で作成します。
- 実データ由来の氏名・住所・連絡先・口座情報などを、README・テスト・ログ等に含めません。
- 開発には AI コーディングアシスタント（Claude Code）を使用していますが、AI には実データを読ませず、架空データのみで開発・テストを行います。実データは `data/` に置き、Claude Code 等の外部 AI に渡さず、本人がローカルで処理・確認します。
- CLI の画面表示や警告には、実データの値（取引先名・金額等）や元ファイル名を含めない設計としています。
